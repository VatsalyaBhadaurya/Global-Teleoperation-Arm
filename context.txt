follower.py

Product goal
The finished system should let a remote operator open a browser, connect to the robot session, view the follower arm’s wrist/gripper camera and global environment camera, request control, and teleoperate the follower arm remotely through the existing leader-follower stack.

The remote layer should:

stream gripper_cam and global_cam to the browser over WebRTC video tracks

send teleop/state/control messages over a WebRTC data channel in structured JSON form

keep ROS 2 local to each machine rather than exposing raw ROS traffic over the internet

use a signaling server for WebRTC setup and TURN/STUN for NAT traversal

Hosting topology
Host only the coordination services on the cloud. Run robot-facing logic on the local machines.

Cloud-hosted
Signaling server on a public VPS.

TURN/STUN server on a public VPS, likely coturn, possibly same machine as signaling for v1.

Leader/operator side
browser UI

leader gateway

existing leader.py

Follower/robot side
follower gateway

existing follower.py

camera publishers feeding gripper_cam and global_cam

After signaling, media and data should go peer-to-peer when possible, with TURN relay fallback when direct connectivity fails.

System modules
Implement these modules.

1. Operator UI
A browser application for:

viewing gripper_cam

viewing global_cam

seeing connection/session/robot state

requesting and releasing control

triggering enable/disable, clutch, estop, home, gripper open/close

2. Signaling server
A backend service for:

creating and joining sessions

authenticating participants

exchanging WebRTC offer/answer

exchanging ICE candidates

tracking roles and control ownership

session cleanup on disconnect

3. Leader gateway
A process near leader.py that:

subscribes to leader_jointstates

subscribes to or consumes leader_command

packages leader state and control intent into network messages

sends them over WebRTC data channel

receives follower status/ack

4. Follower gateway
A process near follower.py that:

subscribes to follower_jointstates

subscribes to follower_command

subscribes to gripper_cam

subscribes to global_cam

publishes camera video as WebRTC tracks

receives teleop messages over data channel

validates them

injects accepted actions into the local control path used by follower.py

sends status/ack/telemetry back to the operator

5. Shared protocol package

State machine
Implement a clear teleop state machine.

Session states
DISCONNECTED

CONNECTED

READY

CLAIMED

ARMED

CLUTCHED

FROZEN

ESTOPPED

Expected transitions
DISCONNECTED -> CONNECTED after signaling and peer setup

CONNECTED -> READY after video/data are healthy

READY -> CLAIMED after operator gets ownership

CLAIMED -> ARMED after enable

ARMED -> CLUTCHED when clutch is active

ARMED -> FROZEN on stale packet / peer loss / watchdog timeout

ANY -> ESTOPPED on estop

ESTOPPED -> READY only after explicit reset path

Do not auto-arm on reconnect. Require explicit operator action after reconnect.

Ownership model
Only one operator may control the robot at a time.

Implement:

single active owner

ownership token or owner operator id

claim timeout on disconnect

non-owner read-only mode

server-side and follower-side ownership validation

Follower gateway must reject action packets if:

session is not owner

teleop is not armed

estop is active

packet is stale or replayed

Safety rules
Safety is mandatory.

Required checks
stale packet timeout

monotonic sequence validation

ownership validation

estop always available

safe hold/freeze on disconnect

explicit re-arm after reconnect

ignore motion when video/data health is invalid, if configured

Safe behavior
if data channel dies, follower enters FROZEN

if signaling disconnects but data is alive, continue only if peer is healthy and watchdog permits

if peer fully dies, freeze

if estop received, no motion commands should be accepted until reset

if command packet age exceeds threshold, freeze and publish error state

WebRTC transport rules
Video
Use separate WebRTC video tracks for gripper_cam and global_cam.

gripper_cam is priority stream.

global_cam can degrade first under bandwidth pressure.

Data channel
Use data channel for:

ownership

state

commands

heartbeat

latency

acks/errors

Suggested rules:

frequent leader-state packets: latest-wins semantics

critical commands like estop/claim/release: reliable delivery path

include timestamps and sequence ids in all actionable messages

How action flows end to end
Operator opens browser UI.

Browser connects to signaling server.

Follower gateway connects to signaling server.

Leader gateway connects to signaling server.

Signaling coordinates WebRTC connection.

Follower gateway starts streaming gripper_cam and global_cam as video tracks.

Operator sees video and status in read-only mode.

Operator requests control.

Signaling/server grants ownership.

Operator arms teleop.

Leader gateway sends teleop.leader_state packets from leader_jointstates.

Follower gateway receives packets, validates them, then injects them into the local control path that follower.py uses.

follower.py drives the arm locally.

Follower gateway sends teleop.follower_state and status back.

Browser updates telemetry.

On disconnect or stale packets, follower gateway freezes teleop and reports FROZEN.

How cameras flow end to end
Robot-side camera nodes publish gripper_cam and global_cam.

Follower gateway subscribes to those topics.

Follower gateway encodes frames into browser-compatible WebRTC video.

Browser receives both video tracks and renders them in the UI.

Build a browser-based remote teleoperation layer around existing ROS 2 leader.py and follower.py. Use WebRTC video tracks for gripper_cam and global_cam, WebRTC data channels for structured JSON teleop/state messages, a signaling server for offer/answer and ICE exchange, a leader gateway to bridge leader_jointstates and leader_command, and a follower gateway to bridge follower_jointstates, follower_command, and camera topics while injecting accepted remote commands into the local follower control path.
